## P0-1 · worktree 层没有实现（最大的一个）

### 问题

§7 整节建立在 wtpool 上，而 wtpool 是另一台机器上未发布的 CLI，这台机器没有。
连带 `treehouse-vs-wtpool.md` 的结论「不整体替换，§7 保持用 wtpool」**也失效了**——没有 wtpool 可以「保持」。

所以真正的选择不是「treehouse 还是 wtpool」，而是下面三个。

### 三个选项

#### A. yan 自带池：`yan tree get | return | status`

不是独立二进制，是 yan 的一个子命令。

- **分支感知从第一天就有**：`yan tree get --base <集成分支> --branch <子分支>` 一步到位，
  §2.1 那个「treehouse 恒定 detached HEAD、不认识分支」的结构性不匹配根本不会出现
- **还树判据就是 yan 自己的弱判据**（§7 那两行），不是 treehouse 的「已并入 default branch」。
  于是正常下工的还树直接成功，**不需要习惯性 `--force`**——而 §9.2 明确把 `--force` 列为禁止动作
- **顺手把调研里认定「treehouse 更好」的三样抄进来**：随机 `lease_id`、条件还树、`--json`
- **`yan tree get --help` 被当成 holder 标签租走一棵树**（§12.3 那个 bug）自然消失
- 符合设计原则 4：所有能力都是 CLI，user 和 agent 看到同一份现实，且只装一个东西

代价：约 200–250 行，占 0→1 总预算（~2350 行）的一成。

#### B. 拿 treehouse 当纯目录池，分支这层自理

- 零实现成本，装着且在用
- 但**每一次正常还树都会撞上它的 unlanded 守卫**：yan 的子分支合回的是**集成分支**，
  永远不是 default branch，所以在 treehouse 眼里永远 unlanded。
  于是 `return` 得长期带 `--force` / `destroy --include-unlanded`（文档标注 *irreversible data loss*）。
  **把最后一道防线变成日常动作，这是最糟的一种妥协**
- 另有一条本机实测过的风险：宿主机死掉后，死掉的 worker 的 slot 会被标记为 available，
  下一次取树可能拿到同一个目录，两个任务指向一棵树。
  这正是 `lease_id` 要解决的问题，而 treehouse 的占用判据以进程为主

判断：现在便宜，之后昂贵且不安全。

#### C. 0→1 完全不做池：一 shift 一次 `git worktree add`，下工 `remove`

- 最小，约 40 行
- 丢掉依赖 / 构建缓存复用。§7 说「monorepo 开 3 棵树 = 3 份依赖安装」，
  **没有池的话是每个 shift 都装一次**，不是只有首次
- 0→1 验收是单 unit 单 shift，痛点要到 1→2 多 shift 并发才显现
- 还树的安全守卫无论如何都要写，这部分省不掉

### 倾向

**选 A。** 理由是 C 省下来的东西比看起来少：分支感知、还树安全判据、孤立 commit 守卫这三块
A 和 C 要写的是同一份代码；A 比 C 多出来的实质上只是「复用目录而不是删掉」加一个 lease 文件，
大约 80 行。而那 80 行换回的是 user 明确点名过的真实成本（依赖重装）。

**命名**：建议就叫 `yan tree`，不另起一个 wtpool 式的独立工具。一次安装、一个仓库、一套文档。
代价是它不能在 yan 之外复用——但 user 在另一台机器上本来就有 wtpool 干那件事。

### 若采纳，要改的地方

- §7 整节重写（对象从 wtpool 换成 `yan tree`，还树判据不变）
- §12.3 那条 bug 删除
- §11 的行数估计 ~2350 → ~2600，脚本清单加 `yan tree`
- `treehouse-vs-wtpool.md` 加一段结论修订：调研的判断依然成立，但前提（wtpool 可用）不成立

## P0-2 · forge：设计写的是 GitLab，手上只有 GitHub

### 问题

设计是 GitLab 原生的：MR、`glab mr list --source-branch`（§6.4）、
「CI 红了由 yan 查 GitLab 发现」（§5.3）、`end` 判定查 GitLab 上的 MR 状态（§6.4）。

两个分开的麻烦：

1. `glab` 没装。这条能修，但要能测就还需要一个真实可访问的 GitLab 实例和鉴权
2. **更硬的一条：0→1 验收（§11）没法在 yan 自己身上跑通。**
   yan 这个仓库在 GitHub 上。而验收要求走完
   「一句话需求 → unit → shift → 子分支 MR → 下工还树 → 对外 MR → user 说合 → 合掉」，
   这需要一个跑在「代码真的会去调用的那个 forge」上的仓库

### 三个选项

| | 做法 | 代价 | 结果 |
| --- | --- | --- | --- |
| A | 薄接缝 `lib-forge.sh`，两份实现，按 `repos.json` 里的 per-repo 字段选 | +80 行 +1 文件 | yan 能在自己身上开发（GitHub），也能在公司用（GitLab） |
| B | 只做 GitLab，找一个 GitLab 项目当靶子 | 0 行，但需要现在就有可用的 GitLab | 自举不了，验收要借外部仓库 |
| C | 0→1 只做 GitHub，1→2 再移植 | 0 行 | 最快跑起来，但 0→1 的产物对真实工作没用 |

### 倾向

**选 A。** 它不是「backend 抽象层」——§11「明确不做」里禁的是插件框架。
§5.7 已经为 `lib-term.sh` 立过同一个先例：**内聚成一个文件里的几个函数，不是框架**。
forge 侧需要的函数比终端还少，四个左右：

```
forge_mr_create      开 MR / PR
forge_mr_state       查状态（open / merged / closed / 查不到）
forge_mr_merge       合
forge_ci_state       查 CI
```

而且它和 P0-3 耦合：如果子分支不上远端（见下），子分支那一级根本没有 MR，
forge 的接触面立刻小一半。

## P0-3 · §12.5 不是细节，是结构决策

设计自己在 §12 列了 5 个待定，其中 **#5「子分支要不要 push 到远端」不是待定项，是必须先定的结构决策**——
文档自己写了：「若采纳，§5.3 的 shift 下工条件、§6.1 的图、§9.2 的授权表都要跟着改」。

而且它还有一个文档没写出来的连锁后果：

> **子分支不上远端 ⇒ 没有子分支 MR ⇒ §6.2 的「两级 review」塌成一级。**
> 内部验收关口从「user 在 GitLab 上 review 一个 MR」变成「yan 本地合 + user 看 diff」。

这一条必须和 §6.2 一起判断，不能只看 §12.5 那张表。

同时它有一个正面后果值得注意：**下工判据会变强。**
从「子分支 MR 已合」变成「集成分支已含子分支 HEAD 且已 push」——
后者是更强的「有副本」证明（集成分支要么交付、要么被新一轮基于，活不丢），
而 §7 的还树安全判据正好吃这个。

它还直接影响 P0-1 和 P0-2 的规模：不上远端 ⇒ yan 要本地合 ⇒
`yan tree` 需要一个「短租一棵树做合并」的路径（`yan sync` 本来就要这个，复用），
forge 侧则少掉整个子分支 MR 的接触面。

**必须在写 `yan shift new` / `yan shift done` / `yan sync` 之前定。**

### 其余四个待定的优先级

| 待定 | 是不是 0→1 阻塞 | 说明 |
| --- | --- | --- |
| §12.4 task id 格式 | ✅ 是 | 写 `yan task new` 之前要定。而且它进分支名（§6.5 `yan/<task>-<unit>-<sid>`），所以短的更好。倾向 `t042` 式序号，可读的标题住在 `brief.md` 和 `log.md` 的标题行 |
| §12.1 `$YAN_HOME` 版本化 | ❌ 否 | 随时能加，`git init` 一下的事 |
| §12.2 `tasks/` 裁剪策略 | ❌ 否 | 0→1 根本没有积累量 |
| §12.3 wtpool `--help` bug | — | 若 P0-1 选 A，自然消失 |

## P0-4 · tmux / herdr：不是阻塞，但值得确认意图

tmux 3.6 装着，所以 §5.7 的 0→1 路径没被卡。这条从「担心」降级为「确认」。

需要 user 拍板的只有一句：**yan 要不要活在自己的 tmux 世界里？**
这台机器日常用 herdr，yan 起一个独立的 tmux session 在技术上完全没问题（两个多路复用器互不干扰），
但屏幕上会同时有两套容器。

有两条本机记录下来的证据支持**先按设计走 tmux**：

- herdr 0.7.5 在宿主恢复后会丢掉 agent 的启动参数，恢复出来的 agent 停在手动确认模式，
  看着活着但什么都不做
- 往 herdr 后端发按键（`BTab` / `S-Tab`）不生效

这两条都是这台机器、这个版本上的实测。tmux 是验证过的参考实现。
建议 0→1 就按 §5.7 写的用 tmux，把上面两条记进 learnings，留给第二份实现的那天。

## P0-5 · yan 仓库自身的交付姿态

这不是 yan 的设计问题，是「我们怎么造 yan」的问题，但也得先定：

| 选项 | 含义 |
| --- | --- |
| `no-mistakes` | 每次改动过完整的自动化流水线（review / 测试 / 文档 / CI）再开 PR |
| `direct-PR` | 直接推分支开 PR，质量把关靠 user + CI |
| `local-only` | 不开 PR，本地分支 |

有点意思的是：**yan 自己的设计明确不引入 no-mistakes**（§11「关于 no-mistakes」），
理由是「质量把关落回 user + CI + 同事 review，这本来就是正常团队的做法」。
在 yan 这个仓库上用不用它，是另一件事，但值得一起想。

暂按 `no-mistakes` 注册（默认值），随时可改。
