## 2026-08-05 · 动工前的三个 P0

三个都已敲定，并且已经折进设计文档。

| | 决定 | 理由 | 展开在 |
| --- | --- | --- | --- |
| **P0-1** | yan 自带 worktree 池（`yan tree get \| return \| status`） | 整个项目不依赖一个额外的东西。treehouse 里值得抄的三样——随机 `lease_id`、条件还树、`--json`——一并抄了进来 | design §7 |
| **P0-2** | GitLab 和 GitHub 都支持，抽一层 forge deep module | 工作用 GitLab，日常用 GitHub，两个都是真实需求。附带收益：0→1 的验收标准可以在 yan 自己身上跑通 | design §8.4 |
| **P0-3** | 子分支推到远端，两级 MR 都保留 | 每个 shift 一个独立 MR，就是 user review 的主要方式 | design §12「已定」、design §6.2 |

P0-3 掉出来一条不变量，已经写进设计：**下工和删分支都以 MR 状态为准，不以 git 祖先关系为准**
（design §5.3）。

## 2026-08-05 · 0→1 用 tmux，不用 herdr

design §5.7 写的就是 tmux，这里补两条本机实测的证据，说明为什么现在不换。
两条都是这台机器、这个版本（herdr 0.7.5）上量到的，建议一并记进 `mem/learnings/`，
留给写第二份 `lib-term.sh` 实现的那天：

1. 宿主恢复后 herdr 会丢掉 agent 的启动参数，恢复出来的 agent 停在手动确认模式，
   看着活着但什么都不做。
2. 往 herdr 后端发按键（`BTab` / `S-Tab`）不生效。

tmux 是验证过的参考实现，所以 0→1 按 design §5.7 走它。yan 起一个独立的 tmux session
在技术上没问题（两个多路复用器互不干扰），代价是屏幕上会同时有两套容器。

## 还没查的三件事

都要看一眼公司仓库的配置，都很便宜。它们是 P0-3（子分支推到远端）掉出来的。

1. **CI 触发范围。** 看 `.gitlab-ci.yml` 的 `workflow:` / `rules:`：
   pipeline 是所有分支都跑，还是只在 MR 上 / 只在受保护或特定前缀分支上跑？
   design §6.5 把「团队 CI 常按分支前缀触发，每个 shift 白烧一次昂贵 CI」列成了
   「不要从集成分支派生子分支名」的理由之一，但推上去之后这件事跟命名无关了，
   是无条件成立的。若所有分支都跑，便宜的解法是推子分支时带 `git push -o ci.skip`，
   让 CI 只在 MR 上跑一次。
   > ⚠️ 这一条和 design §12「已定」里的「CI 的重复触发成本经 user 判断可以忽略，不做处理」
   > 有冲突，两处都是 2026-08-05 写的。留待 user 裁决，本次整理不替它做决定。
2. **分支保护 / push 规则会不会拒绝 `yan/*`。** 有些团队对分支名有强制规范。
3. **已合的远端子分支要真的被删掉**，否则服务器上会堆一堆 `yan/*`。
   design §7 的下工顺序已经写了这一步；开内部 MR 时直接勾上「合并后删除源分支」最省事。
